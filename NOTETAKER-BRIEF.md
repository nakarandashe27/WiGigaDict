## 1. Что это и зачем

Wispr Flow (референс продукта, https://wisprflow.ai) имеет два режима:

- **Dictation** — то, что WiGigaDict уже строит: живой микрофон → локальный ASR → вставка текста в активное окно.
- **Notetaker** — импорт **готовой записи** встречи/созвона (видео или аудио, локальный файл или ссылка) → транскрибация в текст. **Этого в проекте нет и изначально не было заложено.**

Задача: добавить Notetaker как **второй режим рядом с Dictation**, переиспользующий тот же локальный ASR-核, но с другим входом (импорт записи) и другим выходом (документ-транскрипт, а не вставка в окно).

Notetaker — НЕ отдельное приложение и НЕ копия Telegram-бота. Бот (`c:\transcribator`) берётся только как **референс проверенного потока** (ссылка → скачивание → транскрибация). Его архитектуру (Python-движок, pyannote, облачный DeepSeek) переносить НЕЛЬЗЯ — она нарушает принципы WiGigaDict.

## 2. Объём v1 (зафиксировано владельцем 2026-08-21)

**В scope v1:**
- Вход: **локальный файл** (видео/аудио) И **публичная ссылка Яндекс.Диска**.
- Декод произвольного контейнера → PCM S16LE 16 кГц mono.
- **Длинный ASR с таймкодами** (тем же ASR-движком, что и Dictation, но long-form).
- Выход: **плоский транскрипт с таймкодами** (сегменты `[время] текст`), сохраняемый как артефакт + просмотр в приложении + экспорт (txt/srt/vtt).

**НЕ в scope v1 (сознательно отложено):**
- ❌ **Диаризация** («Спикер N», кто что сказал). В боте это pyannote (Python) — в WiGigaDict Python в проде запрещён. Путь без Python — ONNX-диаризация (sherpa-onnx: pyannote-сегментация + speaker-embeddings через ORT) — это **главный research-риск, вынесен в v2**.
- ❌ **Саммари/заметки по встрече.** Требует LLM; облако (DeepSeek) запрещено принципами → только локальная LLM, отдельная тяжёлая модель на 8 ГБ GPU. Отложено в v2.
- ❌ Любое облако, сервер, телеметрия, аккаунты, оплата (как и во всём MVP).

## 3. Референс-поток бота (что переиспользовать концептуально, НЕ код)

Файлы в `c:\transcribator` — рабочий образец потока «ссылка → результат»:

| Файл бота | Что делает | Что взять в Notetaker | Что НЕ переносить |
|---|---|---|---|
| `pipeline/downloader.py` | `YandexDiskResolver`: `GET https://cloud-api.yandex.net/v1/disk/public/resources/download?public_key=<ссылка>` → `href` → **стрим-скачивание** с лимитом размера (`FileTooLargeError`), имя из `href` | Логику резолва Я.Диск-ссылки + потоковое скачивание с лимитом → переписать на Rust (`reqwest`+`rustls`) | — |
| `pipeline/transcriber.py` | REST-клиент к движку GigaAMGUI: submit файла → poll статуса → download результата | Паттерн «submit→poll→result» как модель job'а | ❌ REST к Python-движку — в WiGigaDict это **локальный Rust ASR-sidecar** (NDJSON IPC) |
| `taskqueue/worker.py` | `JobQueue`: async-очередь, `status_cb` (прогресс), `notifier` (deliver/fail), опциональный персистентный `store`, **восстановление незавершённых при старте** | Паттерн очереди + прогресс + восстановление → в WiGigaDict это Tokio-задачи + durable job-state в SQLite (уже в стеке) | ❌ aiogram/Telegram-нотифаер |
| `models.py` | `Job{url,...}` → `Transcript{text, source_filename}` → `MeetingResult{transcript, protocol, docx}` | Форма сущностей задачи/результата | ❌ `protocol`/`docx` (саммари вне v1) |
| движок `C:\GigaAMGUI` (ffmpeg → GigaAM + pyannote → md/timecodes/srt/vtt) | Показывает: ffmpeg-декод в 16k mono, формат таймкодов `[MM:SS - MM:SS] текст` | Формат декода (16k mono) и формат таймкод-выхода | ❌ pyannote, ❌ REST-обёртка на FastAPI |

## 4. Целевой поток Notetaker v1 (в архитектуре WiGigaDict)

```
[UI: выбрать файл  ИЛИ  вставить ссылку Я.Диск]  (явное действие пользователя)
        │  (Rust command, privileged — не из overlay-capability)
        ▼
[Ingress]  локальный файл: путь              │  Я.Диск: resolver → href → reqwest+rustls
           (никакой сети)                     │  стрим в .part → flush/sync → atomic rename
        ▼
[Decode]  ffmpeg: контейнер (mp4/webm/mkv/mp3/m4a/…) → PCM S16LE 16k mono
        │  → durable artifact (два-хранилища commit, как у Dictation-аудио)
        ▼
[ASR long-form]  тот же Rust ASR-sidecar, но chunking/VAD path (GigaAM ≤25с → чанки;
        │  whisper.cpp long-form нативно) → сегменты {start, end, text}
        ▼
[Assemble]  плоский транскрипт с таймкодами (стич сегментов по времени)
        ▼
[Egress]  сохранить артефакт (SQLite + файл) + показать в приложении +
          экспорт txt/srt/vtt   (НЕ вставка в активное окно — это егресс Dictation)
```

Прогресс, отмена и **восстановление после краша** обязательны (файлы длинные, минуты-часы): durable job-state в SQLite + startup catch-up (уже принято в стеке), частичный транскрипт восстановим (per-chunk commit).

## 5. Решения, которые Notetaker навязывает архитектуре (материал для прожарки)

1. **Сеть входит в основной pipeline.** Стек прямо говорит «Сеть не участвует в основном pipeline» (только модели/апдейты, с checksum). Ссылка Я.Диск это нарушает: тянем **пользовательский контент** (checksum'а нет). Митигация: только явное действие пользователя, никакого авто-fetch; **локальный файл — дефолтный чистый путь без сети**. Это пункт №1 на прожарку: допустимо ли, и как оформить (отдельная capability, а не core-принцип).
2. **FFmpeg становится runtime-зависимостью.** Сейчас в стеке: «FFmpeg 8.1.1 найден, но НЕ обязательная runtime-зависимость MVP». Notetaker декодит произвольные контейнеры/кодеки → ffmpeg нужен. Решить: **бандлить ffmpeg** в установщик (как sidecar-бинарь, вызывается Rust shell) vs требовать у пользователя vs Rust-нативный декод (`symphonia` покрывает аудио-контейнеры, но НЕ видео-контейнеры/кодеки). Плюс лицензия сборки ffmpeg (LGPL vs GPL). Рекомендация к прожарке: бандл LGPL-сборки, вызов из shell, тот же durable-паттерн.
3. **Long-form ASR обязателен.** Официальный `GigaAM.transcribe` — до 25с; `transcribe_longform` тянет pyannote+HF-токен (запрещено). Значит нужен **свой детерминированный chunking/VAD без Python и без токена** — это уже требование ASR-gate в стеке, Notetaker его усиливает (часы аудио, стич таймкодов без дрейфа). whisper.cpp long-form — нативно.
4. **Новый егресс и сущности.** Dictation вставляет текст в окно; Notetaker создаёт **документ-транскрипт**. Нужны сущности (напр. `ImportJob` / `Recording` / `Transcript`+`Segment`), ложащиеся на существующую модель (18 сущностей) и two-storage commit. Где хранить и как показывать — переиспользовать «управлять-историей»?
5. **Приватность записей третьих лиц.** Запись встречи содержит голоса других людей. Локально — ответственность пользователя, но зафиксировать в границах/безопасности (как в боте отмечено про клиентские голоса).

## 6. Открытые решения (вопросы владельцу до кодинга — прожарить)

- **FFmpeg:** бандл vs требование vs `symphonia`; какая лицензионная сборка; размер установщика.
- **Я.Диск resolver:** только публичные ссылки? приватные/с истечением/большие файлы? политика лимита размера и длительности; что делать при `href` без имени/формата.
- **Лимиты:** макс. размер/длительность файла v1; место на диске под декодированный PCM (~115 МБ на час 16k mono — ок).
- **Chunking/VAD:** какой алгоритм разбиения, окно/overlap, точность стич-таймкодов; общий ли он с Dictation ASR-gate.
- **Форматы экспорта v1:** txt/srt/vtt — достаточно? docx позже?
- **UI:** отдельный экран Notetaker vs пункт в основном окне; как показывается прогресс длинной задачи и отмена.
- **Швы под v2 (не строить, но не заблокировать):** диаризация через sherpa-onnx (ONNX-путь без Python); локальный LLM-саммари. Сегменты ASR должны нести время, чтобы v2-диаризация могла присвоить спикеров постфактум.
