# Главный кирпич

## Статус решения

✅ **Принято:** вариант 3 — без глобальной унификации. `DictationSession` остаётся aggregate root Dictation; M2 добавляет отдельный `NotetakerJob` со своим lifecycle.

Унификация применяется только внутри lifecycle диктовки. Конфигурация, модели, glossary и diagnostics не наследуются от общего `Record` и сохраняют собственные строгие схемы.

## Сущности, выведенные из контекста

| Сущность | Зачем существует | Отличающий lifecycle |
|---|---|---|
| Диктовочная сессия | Сквозной `hold → record → transcribe → clean → insert/recover` | Короткоживущая операция, но хранится по retention |
| Аудиоартефакт | Восстановить завершённую диктовку до появления текста | Временный, удаляется после безопасной точки |
| Версия транскрипта | Хранить raw и cleaned без перезаписи | Неизменяемая версия внутри сессии |
| Снимок target | Проверить, куда разрешено вставлять | Фиксируется при key-down, перепроверяется перед insert |
| Попытка доставки | Зафиксировать механизм, исход и риск дубля | Append-only; у сессии может быть несколько попыток |
| Событие сессии | Восстановить FSM после crash и объяснить отказ | Append-only, монотонная последовательность |
| Recovery state | Показать unresolved и управлять retry/copy/resolve | Живёт до явного resolution |
| Model package | Описать веса, источник, checksum и установку | Версионируемый локальный ресурс |
| Runtime profile | Связать engine, model, device и health | Долгоживущая конфигурация с readiness |
| Glossary entry | Хранить spoken form и preferred spelling | Пользовательский изменяемый справочник |
| App/cleanup profile | Определять допустимую очистку и поведение по режиму | Версионируемая настройка; часть после MVP |
| Diagnostic event | Измерять latency и причины отказа без содержимого | Append-only с отдельным сроком хранения |
| Notetaker job | Импортировать и транскрибировать готовую запись | Длинная resumable-задача без target/insertion lifecycle; M2 |

Локальный Windows-пользователь не является отдельной бизнес-сущностью MVP: авторизация наследуется от текущей Windows-сессии, аккаунта и многопользовательской БД нет.

## Вариант 1 — один универсальный `Record`

### Гипотеза

```text
Record {
  id
  type
  schema_version
  state
  properties
  parent_id?
  order?
  created_at
  updated_at
}
```

Все сущности становятся `Record` с `type = session | audio | transcript | delivery | event | model | glossary | profile | diagnostic`.

### Что выигрываем

- один CRUD, экспорт, soft delete и механизм миграции;
- легко добавлять новые типы без новой таблицы;
- единая оболочка истории изменений.

### Что проигрываем

- обязательные поля и допустимые переходы скрываются в `properties`;
- сложнее доказать атомарность session journal и запрет незаконных состояний;
- универсальный CRUD создаёт действия, которые для append-only событий недопустимы;
- ошибки schema/type проявляются во время выполнения;
- WiGigaDict незаметно превращается в платформу данных вместо узкого инструмента.

**Вердикт:** не рекомендуется. Экономия на таблицах слабее риска для blocker R-01.

## Вариант 2 — два кирпича: `Session` и `ManagedResource`

### Гипотеза

```text
Session {
  id
  state
  state_version
  started_at
  finalized_at?
  target_snapshot
  retention_class
  pinned
  resolved_at?
}

ManagedResource {
  id
  type
  schema_version
  state
  properties
  source?
  checksum?
  enabled
  created_at
  updated_at
}
```

`Session` является корнем аудио, transcript versions, delivery attempts и session events. `ManagedResource` объединяет `model_package`, `runtime_profile`, `glossary_entry`, `app_profile` и versioned settings. Diagnostic events остаются отдельным техническим журналом.

### Что выигрываем

- operational pipeline отделён от долгоживущих пользовательских ресурсов;
- общие операции enable/disable/import/export/version доступны всем ресурсам;
- модель хорошо расширяется вторым ASR adapter и будущими app profiles;
- меньше сущностей верхнего уровня.

### Что проигрываем

- `ManagedResource.properties` требует отдельной строгой схемы для каждого `type`;
- glossary entry, model package и hotkey profile имеют слишком разные правила;
- общий lifecycle `enabled/state` рискует стать набором исключений;
- generic resource API может оказаться преждевременной абстракцией.

**Вердикт:** жизнеспособно, если приоритет — быстрый рост числа профилей после MVP.

## Вариант 3 — без глобальной унификации, с `DictationSession` как aggregate root

### Гипотеза

Главный бизнес-кирпич — строго типизированная `DictationSession`. Она владеет ссылками на аудио, immutable transcript versions, target snapshot, delivery attempts и ordered session events. Model packages, runtime profiles, glossary entries, settings и diagnostic events остаются отдельными сущностями с собственными схемами и сроками жизни.

```text
DictationSession {
  id
  state
  state_version
  started_at
  finalized_at?
  target_snapshot_id
  raw_transcript_id?
  cleaned_transcript_id?
  retention_class
  pinned
  resolved_at?
  last_error_code?
}
```

### Список вариантов внутри сессии

- `AudioArtifact` — временный recoverable input;
- `TranscriptVersion(kind = raw | cleaned)` — immutable text artifact;
- `DeliveryAttempt(method = unicode | send_input | clipboard)` — append-only outcome;
- `SessionEvent` — ordered state transition with source;
- `TargetSnapshot` — immutable identity и privilege metadata.

Это не наследование от универсальной записи: каждый тип имеет собственную схему и инварианты, а `DictationSession` связывает их как aggregate root.

### Что выигрываем

- illegal states и обязательные поля проверяются типами и схемой;
- проще доказать atomic recovery, идемпотентность и retention;
- append-only сущности нельзя случайно редактировать generic CRUD;
- ошибки локализуются в конкретном lifecycle;
- новый разработчик видит предметную модель, а не набор условных `properties`.

### Что проигрываем

- больше явных таблиц/структур и миграций;
- экспорт и удаление реализуются через orchestrated операции, а не один generic endpoint;
- добавление нового типа требует схемы, тестов и миграции;
- app profiles и glossary не получают общий UI автоматически.

**Вердикт:** **рекомендуется**. У WiGigaDict мало сущностей, но очень разные lifecycles и жёсткий recovery-инвариант. Явная модель дешевле в сопровождении, чем универсальная платформа с условной валидацией.

## Принятое решение

Выбран вариант 3: `DictationSession` — главный aggregate root, но не универсальный базовый класс для всей системы. Это соответствует [модульному монолиту](../01-обзор/границы.md#физическая-архитектурная-граница), [durable session journal](../01-обзор/карта-системы.md#основной-поток) и blocker [R-01](../../idea/07-risks/operational.md#r-01--результат-теряется-при-сбое).

## Второй aggregate: `NotetakerJob`

Notetaker не расширяет `DictationSession` nullable-полями и не вводит общий `Record`. Это отдельный aggregate root для потока `source → decode → chunked ASR → transcript → export`:

```text
NotetakerJob {
  id
  status
  stage
  state_version
  source_id
  pause_reason?
  last_error_code?
  completed_at?
}
```

Он владеет source snapshot, managed media artifacts, chunks/checkpoints, ASR attempts, transcript versions/segments и ordered job events. Общими с Dictation остаются только `RuntimeProfile`, ASR adapter/sidecar contract, content-free diagnostics и storage primitives (`.part → flush → rename → DB marker`), но не FSM, target snapshots, delivery attempts или insertion outcome.

Причина разделения — разные инварианты: Dictation обязана доказать доставку текста в Windows target и хранит recovery до resolution; Notetaker работает минуты/часы, имеет ingress/decode stages, паузу/очередь и создаёт самостоятельный transcript document до явного удаления. Решение зафиксировано в [ADR-001](../06-решения/журнал-решений/2026-08-21-001-notetaker-как-отдельный-режим.md).

## Решение пользователя

Вариант 3 подтверждён пользователем. 21 августа 2026 года владелец отдельно подтвердил `NotetakerJob` как второй aggregate без общей nullable-сущности. Варианты 1 и 2 сохраняются выше как сознательно не выбранные альтернативы.
