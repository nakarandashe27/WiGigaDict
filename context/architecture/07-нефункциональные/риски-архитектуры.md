# Premortem архитектуры WiGigaDict

Ниже — разбор спустя год после провала: приложение переписывают с нуля, потому что архитектурные контракты не закрыли указанные пути отказа.

## 3 убийственных риска

Без них продукт умрёт через 3 месяца.

### 1. «Доставлено» означало лишь успешный вызов Win32

- **Что пошло не так.** После вставки в IDE система помечала текст `delivered`, хотя control его не принял.
- **Почему именно здесь.** [Лестница вставки](../05-стек/технологии.md#таблица-технологий) заканчивается `SendInput` и clipboard, а [триггер подтверждённой доставки](../04-потоки/триггеры.md#таблица-триггеров) не задаёт доказательство появления текста для каждого поддерживаемого control; документация также признаёт, что отказ UIPI у `SendInput` не всегда диагностируется.
- **Что сделать сейчас.** В [таблицу триггеров](../04-потоки/триггеры.md#таблица-триггеров) встроить раздел «Контракт доказательства вставки»: для каждого пути и control из support matrix зафиксировать наблюдаемое evidence, а без него оставлять только `uncertain`; acceptance-тест обязан проверять отсутствие ложного `delivered` при смене focus, UIPI и отказе clipboard.

### 2. SQLite и PCM переживали crash как две несогласованные истины

- **Что пошло не так.** После отключения питания база фиксировала завершённую сессию, а recovery открывался без читаемого аудиоартефакта.
- **Почему именно здесь.** [Файловая durability](../05-стек/технологии.md#таблица-технологий) описывает `flush/sync → rename → DB transaction`, но не определяет идентификатор commit, таблицу состояний между файловой и SQLite-фиксацией, проверку hash при restart и repair-решение для каждого разрыва; при этом [zero-loss gate](../03-данные/правила-нерушимые.md#dictationsession-и-zero-loss-gate) требует recoverable artifact после любого crash.
- **Что сделать сейчас.** В [правила DictationSession и zero-loss gate](../03-данные/правила-нерушимые.md#dictationsession-и-zero-loss-gate) встроить «Протокол двух хранилищ»: prepare-record с hash/размером, порядок `fsync` файла и директории, SQLite commit marker, startup reconciliation и repair-матрицу; fault-injection тест обязан обрывать процесс после каждого шага и доказывать ровно один читаемый recovery artifact.

### 3. Накопившиеся ASR-задачи съели память, диск и время ответа

- **Что пошло не так.** Серия коротких диктовок создала неограниченную очередь finalized audio, worker отстал, а приложение перестало отвечать до заполнения диска.
- **Почему именно здесь.** [Async и расписание](../05-стек/технологии.md#таблица-технологий) назначает Tokio и SQLite, а [правила выполнения](../04-потоки/триггеры.md#правила-выполнения) ограничивают только audio callback и одну запись, не устанавливая общий лимит pending sessions, байтов PCM, параллелизма ASR, порядок admission и судьбу задач после restart.
- **Что сделать сейчас.** В [правила выполнения](../04-потоки/триггеры.md#правила-выполнения) встроить durable dispatcher с лимитами `max_pending_sessions`, `max_pending_pcm_bytes` и одним ASR lease, явным отказом до записи при исчерпании бюджета и FIFO-порядком из SQLite; нагрузочный тест обязан превысить каждый лимит, сохранить уже принятые сессии и вернуть shell в работоспособное состояние.

## 4-5 серьёзных рисков

### 4. Обновлённый runtime перестал читать установленную модель

- **Что пошло не так.** После обновления adapter запустился с прежним package, неверно прочитал tokenizer и выдавал испорченный transcript без явной ошибки.
- **Почему именно здесь.** [ModelPackage](../03-данные/сущности.md#модели-и-runtime) хранит один checksum и версию модели, но не фиксирует format ABI, tokenizer/config hashes, набор обязательных файлов и матрицу совместимости adapter–runtime–model; [совместимость найденных моделей](../05-стек/технологии.md#совместимость-найденных-локальных-моделей) прямо указывает, что одних weights недостаточно.
- **Что сделать сейчас.** В строку ASR adapter contract [таблицы технологий](../05-стек/технологии.md#таблица-технологий) встроить подписанный compatibility manifest с ABI, hashes всех частей package, минимальной и максимальной версиями adapter и probe corpus; install и startup обязаны запускать probe, а несовместимый profile обязан оставаться `not_ready`.

### 5. Старый fallback-код тихо стал боевым маршрутом

- **Что пошло не так.** Редкий rollback перевёл пользователей на заброшенный backend, который год не проходил regression и терял сессии при отмене worker.
- **Почему именно здесь.** [Технологический выбор](../05-стек/технологии.md#решение) оставляет победителя ASR открытым, а [ASR gate](../05-стек/технологии.md#asr-gate-что-именно-сравниваем) допускает `transcribe-rs`, прямой `whisper.cpp` binding и тонкий ORT adapter без реестра активного маршрута, владельца, срока жизни fallback и обязательной проверки rollback-пути.
- **Что сделать сейчас.** В строку ASR adapter contract [таблицы технологий](../05-стек/технологии.md#таблица-технологий) встроить реестр маршрутов с единственным default, статусом `experimental/active/retired`, владельцем и датой удаления; release gate обязан прогонять crash/cancel/restart regression для каждого `active` и `rollback` маршрута, а `retired` код удаляется из пакета.

### 6. No-focus overlay крал фокус в самой важной миллисекунде

- **Что пошло не так.** Окно overlay активировалось при отпускании hotkey, поэтому insertion попадал не в исходное поле или вообще не выполнялся.
- **Почему именно здесь.** [Выбор no-focus overlay](../05-стек/технологии.md#таблица-технологий) основан на маленьком `windows-rs` shim и будущем Win32 spike, но [основной поток](../01-обзор/карта-системы.md#основной-поток) уже считает сохранённый target достаточным и не задаёт инвариант проверки, что overlay ни разу не получил foreground/keyboard focus.
- **Что сделать сейчас.** В [раздел No-focus overlay таблицы технологий](../05-стек/технологии.md#таблица-технологий) встроить spike acceptance matrix для Windows 10/11, VS Code, terminal и browser: log foreground HWND на первом/втором toggle key-down и перед insert, а тест допускает delivery только при неизменном target; при провале выбрать native overlay до реализации остального UI.

### 7. Цепочка обновления позволила подменить приложение или модель

- **Что пошло не так.** Злоумышленник подменил manifest и package в канале обновления, а клиент установил вредоносный sidecar вместе с валидным для подменённого manifest checksum.
- **Почему именно здесь.** [Сетевые загрузки](../05-стек/технологии.md#таблица-технологий) требуют HTTPS и SHA-256, а [Updates](../05-стек/технологии.md#таблица-технологий) полагаются на подпись Tauri, но архитектура не определяет доверенный корень для model manifest, key IDs, provenance release, отзыв ключа, защиту от downgrade и проверяемый rollback.
- **Что сделать сейчас.** В [раздел Updates таблицы технологий](../05-стек/технологии.md#таблица-технологий) встроить единый signed-release manifest для app, sidecar и model package с root key, key rotation/revocation, version floor и offline verification; CI обязан отклонять package с чужой подписью, просроченным key и более старой версией.

## Остальные заметки

### 8. Retention удалял строки, но оставлял пользовательские данные на диске

- **Что пошло не так.** После 15 дней история исчезла из UI, но raw text и audio остались в SQLite WAL, `.part`, diagnostic export или забытом managed-файле.
- **Почему именно здесь.** [Правила retention](../03-данные/правила-нерушимые.md#recovery-и-retention) описывают cascade и orphan cleanup, но не содержат полного инвентаря физических копий для DB/WAL/SHM, PCM, `.part`, export и recovery после interrupted delete; [диагностика](../03-данные/сущности.md#диагностика-и-обслуживание) объявлена производным экспортом без lifecycle удаления.
- **Что сделать сейчас.** В [раздел Recovery и retention](../03-данные/правила-нерушимые.md#recovery-и-retention) встроить реестр всех managed-копий, порядок их удаления и журнал незавершённого delete; integration-тест после retention и restart обязан проверить отсутствие доступного transcript/audio по каждому storage key и отсутствие orphan references.

### 9. Чистая установка работала только на машине разработчика

- **Что пошло не так.** Новый пользователь получил installer без работающего WebView2, sidecar runtime или нужных VC/graphics зависимостей и не прошёл первую диктовку.
- **Почему именно здесь.** [Локальная build-среда](../05-стек/технологии.md#локальная-build-среда-на-2026-08-20) перечисляет отсутствующие build tools, а [installer personal alpha](../05-стек/технологии.md#таблица-технологий) обещает NSIS package без списка конечных runtime prerequisites, offline-ветки, preflight и матрицы чистых Windows образов.
- **Что сделать сейчас.** В [раздел Installer personal alpha таблицы технологий](../05-стек/технологии.md#таблица-технологий) встроить install manifest с bundled/prerequisite компонентами, offline import path и диагностируемым preflight; release gate обязан запускать установку и первую CPU-диктовку на чистых Windows 10 22H2 и Windows 11 x64 VM.

### 10. Поддержка не смогла восстановить картину сбоя без утечки текста

- **Что пошло не так.** После потери результата команда получила только разрозненные redacted логи и не установила порядок событий shell, worker и insertion.
- **Почему именно здесь.** [DiagnosticEvent](../03-данные/сущности.md#диагностика-и-обслуживание) хранит component, timing и error code, но не задаёт обязательный build/sidecar/model-manifest fingerprint, IPC correlation sequence, набор пропусков и срок хранения trace; [логи и диагностика](../05-стек/технологии.md#таблица-технологий) ограничиваются `tracing` и rolling JSONL.
- **Что сделать сейчас.** В [раздел Диагностика и обслуживание](../03-данные/сущности.md#диагностика-и-обслуживание) встроить content-free support trace с version fingerprints, session/IPC sequence, reason code и явным `missing_source`; fault-injection тест обязан собирать такой trace для crash worker, focus mismatch и commit failure, а redaction-тест — доказывать отсутствие audio/transcript.

## Вердикт

Три обязательных design mitigation зафиксированы 2026-08-20:

1. [Контракт доказательства доставки](../03-данные/правила-нерушимые.md#контракт-доказательства-доставки) запрещает считать один успешный Win32 call достаточным и требует versioned compatibility evidence.
2. [Commit-протокол SQLite + PCM](../03-данные/правила-нерушимые.md#commit-протокол-sqlite--pcm) задаёт prepare/flush/rename/DB-marker и startup reconciliation для каждого crash window.
3. [Bounded durable dispatcher](../04-потоки/триггеры.md#bounded-durable-dispatcher) ограничивает sessions/PCM/disk/lease до включения микрофона и восстанавливает очередь из SQLite.

Архитектурный gate Stage 10 закрыт на уровне design. Personal alpha всё ещё запрещена, пока эти контракты не реализованы и не пройдены соответствующие fault-injection, load и Windows acceptance tests; backlog ниже делает их release blockers.

## M2 Notetaker premortem — независимая проверка 2026-08-21

Этот раздел подготовлен fresh-context subagent после подтверждения scope; он не меняет M1 gates.

### 3 убийственных риска Notetaker

1. **Notetaker задушил Dictation.** Длинный job удерживал единственный runtime/lease, и live dictation потеряла главный UX. Митигация уже встроена в [Notetaker invariants](../03-данные/правила-нерушимые.md#notetakerjob-и-long-form): абсолютный priority, yield на chunk boundary и load-test через active + 2 queued jobs.
2. **Source/decode/ASR разошлись после crash.** Несогласованные `.part`, PCM, DB checkpoint и transcript породили orphan/duplicate/silent loss. Митигация: отдельный [`NotetakerJob`](../03-данные/главный-кирпич.md#второй-aggregate-notetakerjob), `commit_id` на каждом durable шаге и fault injection между всеми stages.
3. **Long-form stitching тихо портил часы записи.** Короткие tests не нашли seam duplicates/truncation/cumulative drift. Митигация: [30/60-second fixtures и 4-hour soak](../05-стек/исследования/2026-08-21-long-form-asr-spike.md), marker boundaries и round-trip canonical segments → TXT/SRT/VTT.

### Серьёзные риски Notetaker

4. **Yandex стал скрытой availability/security dependency.** Expiry, throttling и hostile redirects выглядели как случайные ASR errors. Митигация: отдельная capability, durable local cache, строгие error classes и [SSRF/expiry/size matrix](безопасность.md#опциональный-yandex-ingress).
5. **FFmpeg bundle оказался GPL либо не читал реальные файлы.** Митигация: один exact shared LGPL profile, source/notices/SBOM и [reproducible build + media matrix gate](../05-стек/исследования/2026-08-21-ffmpeg-lgpl-build-spike.md).
6. **Admission недооценил disk high-water mark.** Source + PCM + `.part` + WAL + queued jobs заполнили диск. Митигация: worst-case reservation на каждый accepted job, 20% margin и soak 4h + 2 waiting на low disk.
7. **Retention удалял нужное или копил чувствительные leftovers.** Митигация: отдельные Notetaker transcript/media policies, physical-copy inventory и cleanup/restore tests после restart.
8. **Pause/cancel остановили UI, но не downloader/ffmpeg/sidecar.** Митигация: cooperative cancellation на каждом stage, supervised child kill-on-timeout и tests pause/draft/delete во время download/decode/ASR/export.

Notetaker остаётся заблокированным для production, пока эти mitigations не выражены тестами M2; наличие архитектурного текста не означает пройденный gate.
