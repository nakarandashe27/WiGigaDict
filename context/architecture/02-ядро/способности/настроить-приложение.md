# Способность: настроить приложение

## Когда применять

- Локальный владелец выбирает hotkey, микрофон, active model, режим cleanup, diagnostics, startup shell или warm-up opt-in.
- Система валидирует сохранённую конфигурацию при запуске без изменения намерения пользователя.

## Когда НЕ применять

- Для автоматического включения автозапуска, telemetry, облака или модели с другим privacy/resource профилем.
- Для изменения Windows security/UAC/firewall ради обхода ошибки.

## Примеры

- **Good:** перед сохранением hotkey проверить конфликт и оставить прежнее значение, если новое недоступно.
- **Bad:** после неудачной вставки включить «Запускать от администратора» без отдельного решения пользователя.

## Что может пойти не так

Конфигурация повреждена, устройство исчезло, hotkey занят, schema version устарела. Валидировать/мигрировать атомарно, сохранять last-known-good, показывать конкретную настройку и не запускать опасный fallback.

Связанные контракты: [configuration entities](../../03-данные/сущности.md#конфигурация-и-персонализация), [матрица прав](../права-доступа.md), [startup/warm-up triggers](../../04-потоки/триггеры.md#автозапуск-и-прогрев).

## Статус реализации M1 / Step 14

`ConfigurationRepository` хранит immutable versioned snapshots в существующей `AppConfiguration`: default/active/last-known-good, optimistic `expected_config_version` и отказ от неизвестного runtime, cleanup contract или исчезнувшего input device. Desktop применяет hotkey, microphone, runtime/cleanup intent и user-level `HKCU\\...\\Run` как одну координированную операцию; при ошибке восстанавливает прежний live hotkey/startup state и не заменяет last-known-good. Startup, warm-up и content-free diagnostics остаются явными opt-in; Step 14 сохраняет и валидирует эти намерения, не добавляя telemetry, cloud fallback или новый ASR worker command.
